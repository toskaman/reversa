# 1. RÈGLE ABSOLUE : 20 SOUS-AGENTS À CHAQUE CYCLE

## 1.1 Architecture de développement

Tu es l'orchestrateur principal : **AGENT-00 / COMMANDER**.

Tu dois constituer une équipe de **20 sous-agents spécialisés**, identifiés AGENT-01 à AGENT-20.

Cette équipe constitue la structure permanente de développement, de recherche, de test et d'audit.

**Objectif impératif : maintenir 20 sous-agents mobilisés à chaque cycle de travail.**

À chaque cycle :

1. Évaluer l'état réel du dépôt.
2. Construire le graphe de dépendances des tâches.
3. Distribuer du travail utile aux 20 rôles.
4. Lancer les 20 sous-agents réellement distincts lorsque l'outil d'orchestration le permet.
5. Exécuter les tâches indépendantes en parallèle.
6. Réserver les tâches dépendantes à la bonne phase.
7. Collecter les résultats de chacun.
8. Intégrer les modifications.
9. Exécuter les vérifications.
10. Recommencer avec 20 nouveaux mandats adaptés à l'état du projet.

Un sous-agent qui n'a plus de fonctionnalité à développer reçoit une mission pertinente d'audit, de revue de code, d'analyse de performance, de concurrence, d'accessibilité, de documentation ou de test adversarial.

Ne crée pas de travail artificiel pour justifier le nombre d'agents.

## 1.2 Gestion des limites réelles

La création de 20 agents réellement indépendants est obligatoire **si l'environnement fournit cette capacité**.

Si une limite technique empêche 20 exécutions simultanées :

- déterminer exactement la limite réelle ;
- conserver les 20 mandats spécialisés ;
- exécuter les mandats par vagues avec la concurrence maximale supportée ;
- maintenir des états et livrables distincts ;
- ne jamais présenter des rôles simulés comme 20 véritables processus ;
- enregistrer la limite dans le journal d'orchestration.

N'utilise pas de faux identifiants d'agents ou de réponses inventées.

Le parallélisme doit augmenter la productivité, pas provoquer des conflits, des pertes de code ou une consommation incontrôlée des ressources.

# 2. DÉFINITION DU PRODUIT

REVERSA n'est pas un chatbot.

REVERSA n'est pas un simple générateur de workflows.

REVERSA n'est pas une copie de n8n, Zapier ou Temporal.

REVERSA est une plateforme d'opérations IA capable de gérer le cycle de vie d'une opération d'entreprise distribuée, de son intention initiale jusqu'à sa vérification finale et, si nécessaire, sa réparation.

## 2.1 Promesse fondamentale

Une entreprise exprime une intention :

"Onboard our new enterprise customer across our systems."

REVERSA doit :

1. Comprendre l'objectif.
2. Identifier les systèmes concernés.
3. Découvrir les actions disponibles.
4. Produire un plan structuré.
5. Détecter les dépendances.
6. Vérifier les permissions.
7. Définir les préconditions.
8. Définir les actions compensatoires.
9. Présenter les changements attendus.
10. Demander une autorisation si nécessaire.
11. Exécuter les actions dans les systèmes configurés.
12. Vérifier les états résultants.
13. Détecter les échecs.
14. Décider s'il faut réessayer, suspendre ou compenser.
15. Exécuter les compensations sûres.
16. Vérifier les états finaux.
17. Produire un rapport d'exécution.
18. Afficher les ressources et événements.
19. Signaler précisément les actions non réparables.
20. Permettre l'export d'une preuve reproductible.

## 2.2 Différenciation stratégique

Notre avantage ne doit pas être seulement un nouveau moteur d'automatisation.

Il doit se situer dans la combinaison :

**AI Planning + Verified Execution + Typed Compensation + State Reconciliation + Evidence.**

Nous devons montrer des garanties concrètes :

- aucune action inconnue ne peut être exécutée ;
- les plans générés par IA respectent un schéma strict ;
- les actions sont exécutées par des connecteurs autorisés ;
- chaque résultat est enregistré ;
- les erreurs entraînent des transitions d'état explicites ;
- les compensations sont vérifiées ;
- les modifications manuelles concurrentes sont détectées ;
- aucune récupération n'est déclarée complète si elle ne l'est pas.

Évite les affirmations absolues comme "every operation can be undone".

La bonne formulation est :

**"Reversible where possible. Accountable everywhere."**

# 3. LE MOMENT WOW ABSOLU

## 3.1 Démonstration phare : Enterprise Onboarding Under Failure

La démonstration principale doit pouvoir être exécutée depuis l'application publique.

L'utilisateur choisit une organisation de démonstration.

Il saisit :

"Onboard Acme Corporation as an enterprise customer. Create their workspace, provision accounts, configure support, prepare billing, assign an account manager and verify everything."

REVERSA génère un plan.

Exemple de graphe :

1. Validate customer.
2. Create CRM organization.
3. Create workspace.
4. Provision user accounts.
5. Configure support queue.
6. Configure billing profile.
7. Assign account manager.
8. Create onboarding checklist.
9. Validate cross-system consistency.
10. Finalize onboarding.

Chaque étape doit disposer d'un état réel et d'une preuve d'exécution.

### Mode normal

REVERSA exécute le workflow.

Le dashboard affiche :

- la progression ;
- les changements d'état ;
- les actions IA ;
- les appels réels ;
- les ressources créées ;
- les validations ;
- les temps d'exécution ;
- les résultats finaux.

### Mode Chaos

Un bouton :

**INJECT FAILURE**

est disponible uniquement dans un environnement de démonstration isolé.

Il permet de provoquer une véritable panne contrôlée.

Exemple :

L'étape de configuration de facturation renvoie une erreur serveur.

REVERSA doit :

1. Détecter l'échec.
2. L'afficher instantanément.
3. Déterminer la politique applicable.
4. Arrêter les actions dépendantes.
5. Vérifier les opérations terminées.
6. Construire la séquence de compensation.
7. Défaire les actions compensables dans l'ordre correct.
8. Vérifier les ressources restantes.
9. Signaler les opérations nécessitant une intervention manuelle.
10. Produire un rapport d'incident.

La démonstration doit montrer les données avant, pendant et après l'échec.

Le jury ne doit pas seulement voir "Rollback successful".

Il doit voir les ressources réellement créées puis supprimées ou rétablies.

### Mode concurrent

Lancer deux workflows qui tentent de modifier la même organisation.

Démontrer la protection contre :
- les doublons ;
- les modifications concurrentes ;
- les versions périmées ;
- les compensations qui supprimeraient une modification plus récente.

### Mode Crash & Recovery

Interrompre un worker pendant une opération.

Le redémarrer.

Montrer que le moteur retrouve son état durable, réconcilie les opérations incertaines et ne répète pas aveuglément les effets externes.

Ce scénario doit être automatisé, mesuré et reproductible.

## 3.2 Une démonstration authentique, pas une animation

Les animations reflètent l'état du système.

L'exécution backend est réelle.

Les API exécutées retournent de véritables réponses.

Les ressources persistent dans des bases de données ou services distincts.

Les tests de pannes produisent de véritables erreurs.

Les événements affichés proviennent de l'exécution.

Le frontend n'invente aucun succès.

Les connecteurs de démonstration doivent être clairement identifiés comme tels.

## 3.3 Connecteurs

Priorité absolue : un ensemble cohérent de services de test suffisamment réalistes pour démontrer une véritable orchestration distribuée.

Construire au minimum :

- CRM Service ;
- Workspace / Identity Service ;
- Support Service ;
- Billing Service, sans vrai paiement ;
- Notification Sink.

Chaque service doit :
- exposer une API réelle ;
- conserver son état ;
- supporter les scénarios d'échec ;
- avoir ses propres ressources ;
- pouvoir être interrogé indépendamment.

**Objectif supplémentaire :** intégrer au moins un service tiers réel dans un environnement de test autorisé.

Exemple possible : dépôt GitHub de test avec création, mise à jour et fermeture d'issues ou de labels.

L'intégration externe ne doit être activée que si les permissions et credentials valides sont disponibles.

Ne pas la remplacer silencieusement par un mock.

# 5. REVERSA TRANSACTION ENGINE

C'est le composant le plus important du projet.

Il doit être fonctionnel avant toute extension spectaculaire.

## 5.1 Modèle d'exécution

Utiliser une machine à états durable.

Exemples d'états du workflow :

- DRAFT
- PLANNED
- VALIDATED
- AWAITING_APPROVAL
- READY
- RUNNING
- VERIFYING
- COMPLETED
- RETRYING
- COMPENSATING
- COMPENSATED
- PARTIALLY_COMPENSATED
- MANUAL_REQUIRED
- FAILED
- CANCELLED

Exemples d'états d'une action :

- PENDING
- CLAIMED
- EXECUTING
- SUCCEEDED
- VERIFYING
- VERIFIED
- FAILED
- RETRY_SCHEDULED
- COMPENSATION_PENDING
- COMPENSATING
- COMPENSATED
- COMPENSATION_FAILED
- UNKNOWN_OUTCOME
- SKIPPED

Définir les transitions autorisées.

Toute transition invalide doit être refusée et journalisée.

Aucun worker ne doit pouvoir écraser silencieusement un état plus récent.

## 5.2 Contrats d'action

Chaque action doit déclarer :

- `action_type`
- `schema_version`
- `connector_id`
- `tenant_id`
- `input_schema`
- `output_schema`
- `preconditions`
- `effects`
- `verify`
- `compensate`
- `compensation_capability`
- `idempotency_key`
- `timeout`
- `retry_policy`
- `risk_level`
- `approval_policy`

Ne pas autoriser une commande shell arbitraire générée par le modèle IA.

L'IA sélectionne uniquement des capacités enregistrées et autorisées.

## 5.3 Compensations typées

Supporter plusieurs niveaux :

**FULLY_REVERSIBLE**

L'action peut être annulée si les conditions de compensation sont satisfaites.

**CONDITIONALLY_REVERSIBLE**

Annulation possible uniquement si l'état externe n'a pas changé de manière incompatible.

**COMPENSATABLE**

Une action correctrice rétablit un résultat métier acceptable sans forcément reconstituer exactement l'historique.

**IRREVERSIBLE**

Aucune opération automatique ne garantit l'annulation.

**MANUAL_ONLY**

Une personne doit intervenir.

**UNKNOWN**

La capacité de compensation n'a pas été démontrée.

Une compensation ne doit jamais être exécutée lorsque ses préconditions ne sont plus valides.

## 5.4 Gestion des effets distribués

Implémenter :

- transactional outbox si nécessaire ;
- atomicité des mises à jour locales ;
- leases de workers ;
- heartbeats ;
- récupération après expiration ;
- contrôles optimistes de versions ;
- verrous ciblés ;
- idempotence ;
- retries bornés avec backoff et jitter ;
- dead-letter handling ;
- détection des opérations à résultat incertain ;
- reconciliation avant de réexécuter un effet externe.

Ne revendique pas une garantie exactly-once sur des systèmes externes qui ne la fournissent pas.

## 5.5 Tests obligatoires

Vérifier :

1. Répétition de la même requête.
2. Retry après timeout.
3. Crash avant persistance du résultat.
4. Crash après effet externe mais avant acknowledgment.
5. Perte d'une réponse HTTP.
6. Deux workers revendiquant la même tâche.
7. Compensation échouant temporairement.
8. Compensation non autorisée.
9. Modification concurrente de la ressource.
10. Action externe à résultat inconnu.
11. Dépendance circulaire dans le plan.
12. Plan partiellement valide.
13. Cancel pendant exécution.
14. Redémarrage de la base.
15. Redémarrage du worker.
16. Double clic sur Execute.
17. Relecture d'un webhook.
18. Tenant invalide.
19. Changement de politique pendant une demande d'approbation.
20. Nouvelle exécution après compensation.

Les assertions doivent vérifier les états et ressources, pas seulement les codes de retour HTTP.
